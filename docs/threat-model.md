# Threat model and security checklist

Who could attack a TOTR server, what they would want, and what stops them. Each control names the test that checks it; "gap" means there is no test or no control yet.

**How far to trust the "Checked by" column (2026-10-15).** Every row that names a server test, and the desktop pin, discovery and origin-guard rows, was *mutation-checked in this audit*: the protection was switched off in the code, the named test was run, and it had to fail (about 130 such changes, listed in "Mutation audit" at the end). Three groups were **not** redone today and rest on the maintainer's earlier checks: the desktop per-server controls (`shellaccess`), web permissions, link opening and the `about:blank` recovery rows (mutation-checked in the desktop break-it run earlier on 2026-10-15), and the Android string logic (`AccessListTest`: 4 of 5 mutants caught, the fifth redundant). A row that could not be proven says **claimed, not proven**. Where a test did not fail at first, a test was added or the row was corrected; those cases are named in the audit.

## Who and what

| Attacker | Wants | Main ways in |
|---|---|---|
| Someone on the internet or the same network, not signed in | Music, accounts, a foothold on the machine | The login page, the open `/app/` and `/static/` paths, guessing passwords or tokens |
| A signed-in member (a friend you invited) | More rights than they were given: other people's data, the admin pages, files on the server | The API with a valid session |
| A machine in the middle (shared Wi-Fi) | Passwords and sessions, or to swap an update for their own code | Plain HTTP, a forged certificate, a forged update |
| A malicious or hijacked update host | Code running as the server | The update download |
| A malicious file (an upload, a `.milk` preset, a tag) | Crashing or taking over a reader | Parsers for tags, images, presets, `.eqf` |
| Someone who gets the database or `.env` | Everyone's passwords, the database | Backups, a leaked file, a pasted password |

Out of scope: someone with root on the server or physical access, and attacks on the music you chose to host (copyright).

## Gaps (honest list)

1. **Certificate pinning** is built for the desktop apps (Linux and Windows shells): trust on first use with a fingerprint check, one pin per server, a changed certificate refused with a warning. **Not yet:** the Android app, the web build opened in a plain browser (the browser's own rules apply), verifying app updates against the maintainer's signature, and removing the built-in default server address.
2. **Android bridge hardening** is mostly done (0.7.3; needs a phone to test): the song sharing asks the person on the phone itself and sends only to the open page's server, and the other controls (server list, probe, install an update) need the per-server Allow described above. Still open: Android cannot tell which *frame* of the open page called the bridge (it only knows the page that is open), so a third-party frame inside an allowed server's page could call it; closing that means moving to `WebViewCompat.addWebMessageListener`, a bigger change. `saveMixtape` takes the server address from the page and is not gated or pinned to the open page's server (it downloads from that address with that address's own cookie). The app also cannot yet trust a server with its own authority.
3. **Throttling is in memory, per process** (fine with one worker).
4. **Uploads** (needs the Upload permission) are now refused unless the tag reader recognises them as audio (they were accepted by extension alone), but the decoders in every app will still open whatever the library holds; they are fuzzed (below).
5. **Fuzzed so far:** the server's parsers (`TOTRsrv/tests/test_fuzz.py`) and the native readers for `.eqf`, equalizer and theme files, visual presets, `.milk` files, formulas and pictures (`DejaVuAmp/tests/fuzz_test.cpp`, `FalseHorizons/tests/fuzz_test.cpp`, built with the sanitizers: 60,000 and 160,000 inputs, no crash, no memory error, no hang). One note: the bundled `stb_image` does a `memcpy` of 0 bytes to a null pointer on some damaged pictures (formally undefined, harmless in practice, upstream code left alone). Songs (tags and decoders) were fuzzed on 2026-10-12, see "Fuzzing songs" below. **Not fuzzed:** `.totrpatch` files.
6. **Load testing is limited** to the runs in performance.md.
7. **The Move to PostgreSQL helper** ran against a real PostgreSQL in the lab container on 2026-10-12 (28 of 29, the one miss was a mistake in the test); the re-run that should say 29 of 29 is still open. It has never touched a real library's database.
8. **Slow connections can use the server up.** The web server has no time limit for a request that is sent very slowly, so about a thousand idle connections from one machine (the service's default limit is 1024 open files) make it stop answering until they go away (it recovered when they closed; nothing crashed). The new unit raises the limit to 65536 and the server is meant for a home network; a firewall limit per address, or a proxy in front, is the real answer if it is ever exposed further. A finished request is not affected.
9. **One person can lock another out of sign-in for 15 minutes** by guessing wrongly on their name from 40 different addresses (the per-name limit). A single address cannot (20 failures per address, 5 per address and name). This is the price of stopping slow guessing from many addresses; the per-name limit is what a real distributed attack runs into.
11. **`totr_maint` can change or delete any item in the `media` tables** at the database level (the rule "only items TOTR created" is kept by the code in `catalog.py`, not by the database). A bug or a hijacked process using that role could damage other data in the database. Tightening it (row rules, or views with `INSTEAD OF` triggers) is a database design change for the owner to decide.
12. **The update service runs as root** and scores 7.8 (exposed) in `systemd-analyze security`; everything it does is checked again by itself (signature, checksum, forward-only, safe unpacking, rollback), and the web app's user can only ask it. A tighter sandbox for it needs the container test, which needs `sudo`.
13. **Throttling and the new invite limit are in memory** (reset by a restart; fine with one process).

## Fuzzing songs (2026-10-12)

Every place that reads the bytes of a song somebody gave us was damaged on purpose (random bytes, a size field blown up to 2 GB or 4 GB, cut short, a piece repeated, one format's body behind another's header, runs of 0x00 and 0xFF, junk) and run. **The player** (`DejaVuAmp/tests/media_fuzz_test.cpp`, built with the address and undefined-behaviour sanitizers, Release): MP3 with ID3v2/v1, FLAC, WAV (8/16/24-bit, float), Ogg Vorbis, and with ffmpeg M4A, ALAC, Opus, WMA, AAC. Each damaged file is opened at a random output rate, read to the end, sought (also to impossible places), read again, and its tags read; the tag parsers (ID3, FLAC comments, Vorbis comments, `cleanTagText`) also get blocks made from nothing with lying sizes. Checks: no crash or memory error, no hang (a watchdog ends the run if one song takes over 60 s), no sample that is not a number, never more sound than the file could hold. Result: about 320,000 damaged songs in six differently seeded 8-minute runs, clean, after fixing the five bugs below. **The server** (`TOTRsrv/tests/test_fuzz_media.py`): mutagen as the server uses it (reading the tags of an upload, writing tags into a downloaded song, checking it plays, the library scan) on generated MP3/FLAC/WAV plus the player's sample songs: 55,000 damaged files in a minute, no exception, no hang, no memory growth. **Pictures** (`FalseHorizons/tests/fuzz_test.cpp`, new `FH_FUZZ_SEED` / `FH_FUZZ_SCALE`): 2.7 million damaged pictures under the sanitizers, clean (the known `stb_image` null `memcpy` note above is the only report).

Found and fixed (all reachable by playing or uploading a hostile file; the first three are in the libraries we ship, which are left unchanged and guarded from our side):
1. **Ogg Vorbis, heap overflow in stb_vorbis 1.22** (the newest): a comment or vendor length near 2^31 or 2^32 makes its allocation size wrap, then it writes the whole claimed length. `oggCommentHeaderSane` joins the first two packets and refuses a file whose comment lengths do not fit the packet before stb_vorbis sees it.
2. **WAV, endless loop in dr_wav**: a `fact` chunk of size 0 to 3 turns into a 2^64 seek, so opening the file hangs the program for ever. `wavChunksSane` walks the chunk list first; RF64, RIFX, Wave64 and AIFF containers (not offered by the player, never tested) are refused.
3. **FLAC, crash after a seek in dr_flac**: after a read failed inside a damaged frame a "successful" seek left pointers unset and the next read dereferenced them. A seek now goes through the start of the file first (which resets that state); a failed seek ends the song.
4. **AAC and others through ffmpeg, crash in `swr_convert`** (our code): the resampler was set from the stream's first description; a stream that changes format, channels or rate in the middle was read as planes that are not there. Now a frame that no longer matches gets a resampler for what it really is, and an impossible frame is skipped. Also an uninitialised `AVChannelLayout` handed to `av_channel_layout_copy` (random stack bytes, crashed on some files).
5. **Not-a-number sound**: a damaged float WAV produced NaN and infinity, and one NaN in an equalizer filter stays there for the session. Every decoder's output now passes through a guard (NaN and infinity become silence, beyond +-64 is held). A WAV or FLAC claiming a sample rate under 1 kHz (a few kilobytes became minutes of upsampled hum) is refused, as the Ogg and ffmpeg paths already did.

On the server: **a song number of 30 digits or a title of megabytes in a tag** (our code) went straight on towards the database (`read_tags`); a track number is now 1 to 4 digits and a name is cut at 500 characters. mutagen itself never crashed or hung.

Each of the three library bugs and the ffmpeg one is kept as a regression input in `DejaVuAmp/tests/data/damaged/` (about 90 KB), played at six rates with seeks at six places on every run; switching the matching guard off makes the test crash, hang or flag (checked for all four). The harnesses took seeds, time and (for pictures) scale from the environment: `DVA_FUZZ_SECONDS`, `DVA_FUZZ_SEED`, `DURATION`, `SEED`, `FH_FUZZ_SCALE`. **Not covered:** the fuzzers do not write tags into M4A/Ogg (mutagen's save path is only exercised by `_tag_file` on whatever it opens), ffmpeg's own demuxers beyond the six formats above, and the system's libraries are as new as the system keeps them.

## Review of join requests, discovery and song offers (2026-10-12)
Read by hand after they were built (join requests and song offers). Fixed in the same change: (1) a signed join request with `"ts": NaN` skipped the clock check (NaN compares false with everything): NaN and Infinity are refused when the payload is read and again at the check, and a deeply nested payload is caught; (2) an offer an admin asked for is accepted at once, so a person who was asked could have sent up to 100 x 300 MB: an offer is now capped at 4 GB in total and a song is refused when the music disk would be left with under 1 GB; (3) on Android a page of whichever server the app is on could have told the phone to send any saved song to that server (a friend's server could take copies of songs saved from another server): the phone now asks first, and sends only to the server whose page is open.
Looked at and fine: SQL (all parameters; `test_sql_audit.py`), who may see or change whose offers (other people's ids read as "no such offer"), file names and folders from tags (made file-safe, never a path), CSRF and size limits on the new routes, text drawn as text everywhere, the join status route (128-bit ids, rate limited), the invite token (never leaves the app; the server holds only its hash).
Accepted or open, on purpose: **a hostile device on the LAN can announce a look-alike server**: the person sees its name, address and authority code, and https servers go through the fingerprint question, plain http protects nothing anyway; **an accepted song is still an unknown file that every client will decode**: the decoders are fuzzed but the accepting person's judgement is the last gate; **`install-key.json` is a plain file** (owner-readable on Linux, no extra protection on Windows): losing it only means the install looks new to the admin.

## Break-it run on the server (2026-10-15)
Method. A copy of the server was started on a dev machine on its own: its own state folder and database (SQLite), its own certificate, test accounts, a loopback-only network (`unshare -rn`), so it could not reach the live server, its database or the Internet. It was attacked with raw requests (paths exactly as written, no client tidying them up). Nothing was sent to the live server except the read-only checks listed under "The live server, read only". The PostgreSQL side (injection through the real driver, role rights) could not be attacked here: there is no PostgreSQL on the dev machine, and the container needs `sudo`.

**Held up (tried, no change needed)**
- *Doing things as someone else.* Every route x 15 path tricks (`//x`, `/./`, `/x/..`, trailing slash, upper case, `;x`, `%2F`, `%00`, backslash, encoded letters) as signed-out and as a member: no variant ever got more than the plain path (117 routes). A member on 13 admin routes: 403. Delegated "users" permission: could not invite an admin, edit own or an admin's permissions, grant what they lack, disable/sign out/delete an admin. Mixtapes, saved data, sessions, offers and requests of another person: 404 every time, including by guessing ids.
- *Sessions.* Cookie flags right on both ports; a planted cookie is never honoured (no fixation); logout ends the session (old cookie 401); a password change signs out the other sessions; the unknown-user and wrong-password answers are identical in text and time (0.12 s each).
- *Cross-site requests.* Foreign `Origin` and `null` refused on every changing route (also the public sign-in); wrong or another person's token refused; a form-encoded post to a JSON route refused. Accepted by design: a request with no `Origin` at all (not a browser) and one where the attacker controls both `Host` and `Origin` (DNS rebinding; the cookie belongs to the real host, so no session comes along).
- *Guessing.* 5 wrong passwords per address and name, then 429 even for the right one; another address can still sign in; a fake `X-Forwarded-For` does not help (ignored unless `TRUSTED_PROXY` is set); 40 failures on one name from 40 addresses stop at 40 (and cost the real person 15 minutes, gap 9).
- *Invites.* 256-bit tokens, all different; a weak password or a taken name does not burn the link; 15 simultaneous redemptions: one account; used, revoked and tampered links refused.
- *Join requests.* Closed by default; junk, oversized, nested, NaN and wrong-type requests refused cleanly (400/413/422, never 500); the status lookup is rate limited (120 per 10 minutes).
- *Files.* Radio media: 9 traversal spellings plus a planted symlink: 404. Uploads: `../../x.mp3`, `..\\x`, absolute paths, NUL, `CON.mp3`, artist `..`: all landed inside the music folder, nothing outside. Range requests of every odd kind: 200/206/400/416, never 500. Static mounts: no listing, no traversal, no source files, `.env`, `.git` or `__pycache__` reachable.
- *Open redirect* (`next`): 11 spellings, none leaves the site. *Methods and CORS:* only the routes' methods answer; a foreign preflight gets no allow headers.
- *Text into the database.* Quotes, `DROP TABLE`, `%s`, `{0}`, NUL and markup stored through mixtapes and saved data: stored as text, accounts intact (SQLite; PostgreSQL by `test_sql_audit.py` only).
- *Does the server run programs?* It never calls ffmpeg or any other program on a person's data (only the native players link ffmpeg's libraries); the only `subprocess` calls are the move helper (fixed command, password on stdin) and the update service (fixed commands). No `shell=True`, `eval`, `pickle` or `yaml.load` anywhere.
- *Signed updates and the move helper*: see the audit table (every protection switched off in turn, each caught).
- *TLS.* Lab: TLS 1.2 and 1.3 only, AEAD suites only, plain http to the https port dropped. The live server: same (below).

**Found and fixed (each has a test that failed before and passes now; `tests/test_hardening.py`)**
1. **A chunked body walked around every size limit (real).** The gate looked at `Content-Length`; a request that also sent `Transfer-Encoding: chunked` and a small `Content-Length` was read in full anyway. 150 MB went into the public sign-in route in 0.9 s, and the upload limit (2 GB) did not apply either: anyone who could reach the port, signed in or not, could use up the server's memory. Fix: any request with `Transfer-Encoding` is refused (411); browsers and the apps always send a length.
2. **A made-up invite link cost a full password hash per try, with no limit (real).** 40 at once kept the server busy for 5 s and `/health` took 1.8 s. Fix: the link is looked up first (a cheap read), failures are counted per address (20 per 15 minutes), the hash is made only for a real link. 0.114 s became 0.006 s per try.
3. **Invite links were written to the request log.** `GET /invite/<token>` is a one-time sign-up link; anyone who can read the log could use one nobody had opened. Fix: the access log shows `/invite/[hidden]` (and the same for the secret join request id).
4. **Numbers too big for the database were 500s** (`/api/tracks/99999999999999999999/audio`; for offers a wrong "needs one more database step"; for users a 503). Fix: both databases' out-of-range errors become a 422.
5. **Any unhandled error went out without the security headers**, as the framework's bare "Internal Server Error". Fix: a catch-all in the gate: generic JSON, headers, the traceback only in the log.
6. **An upload with a long name (a file, an artist or an album) was a 500 after the folders were half made.** Fix: names are cut to what a file system takes, artist and album are at most 300 characters (422), and a refused upload removes the folders it made.
7. **A file called `.mp3` that was not a song was stored** (empty files, random bytes). It is now refused with its name, the same test an offered song already had; an album with one bad file stores nothing.
8. **The upload form read whole files into memory and blocked the server while saving** (known gap since 2026-10-08). Now copied in pieces, off the event loop; measured above.
9. **A server with no installers yet answered every `/static/downloads/...` with a 500 and a traceback in the log** (anyone could fill the log). The folder is created at start.

**Tests that did not prove what they claimed (found by the audit; fixed)**: the join limits (5 per address, 3 per install, 200 waiting, 120 checks) were reset by the test to its own numbers, so changing the real ones failed nothing; HSTS was untested; the "disabled person's session" test passed even with the check gone because disabling also deletes the sessions; the invite one-use and expiry tests passed with the database guard gone because a cheaper check in front caught it first (now the statement itself is tested); the "Content-Length required" test could not fail; the pinning test never used a server certificate that is out of date while its authority is in date (desktop, now added); the error-text filter of the move helper was untested; `test_guards` was named for the page-security rows but tests the database layout (rows corrected); the bare-name scan did not know the view names.

**The live server, read only (2026-10-15):** TLS 1.2 and 1.3 accepted, 1.0 and 1.1 refused; `Strict-Transport-Security`, a nonce CSP on pages, `frame-ancestors 'none'`, `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and a restrictive `Permissions-Policy` on `/login` and `/health`; ports answering from a dev machine (same LAN): 22, 5050 (pgAdmin), 5432 (PostgreSQL), 8443; 80, 443 and 8080 closed. Whether the first three are really limited to the LAN by the firewall cannot be seen from inside the LAN.

## Hardening the way the server runs

What the trial showed, exactly: the server and a client ran inside one transient user service with the restrictions of the new unit (private network, `MemoryDenyWriteExecute`, the system-call filter, the socket families, a read-only system, private `/tmp`), and streaming, a 286 MB upload, offers, join requests and the Status tab worked. A user service cannot enforce `IPAddressDeny` (a connection out was not blocked), and the other limits were not probed for being enforced. Who gets the new unit: a **new install** or a **repaired one** (re-running `deploy/install.sh` rewrites `totr.service`); a signed update (`deploy/apply-update.py`) does **not** touch the unit file, so existing installs keep theirs until the owner re-runs the installer. The first real run of the new unit as a system service is `sudo ./deploy/lab-container.sh test sqlite update` (and `... move`, which also puts PostgreSQL behind it).
