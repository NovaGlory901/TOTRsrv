# Security

Design stance: **treat the app as if it were on the internet**, even though it is reachable only from the home network.

## What is protected, and where

| Risk | Control | Where |
|---|---|---|
| Anonymous access | Deny-by-default gate: every path needs a session unless in `PUBLIC_EXACT/PUBLIC_PREFIX`; fails closed if accounts are not configured | `auth/web.py` (`gate`) |
| Privilege escalation | `member` vs `admin` plus per-user permissions; each protected route names the permission it needs (`PERMISSION_PREFIX`, closed by default); you can only grant what you hold, never to yourself, and only admins can touch admins | `auth/web.py`, `auth/permissions.py`, `auth/service.py` |
| Stolen/leaked database | Passwords are Argon2id hashes; session and invite tokens stored only as SHA-256; `robots` role cannot read account tables (it sees the music only through TOTR's views) | `auth/passwords.py`, `auth/store.py`, `sql/auth_schema.sql` |
| Password guessing | 12-128 char policy; throttling 20/5/40 failures per 15 min (address / address+user / user); identical response for wrong password and unknown user; a dummy hash is verified for unknown users so timing does not leak | `auth/passwords.py`, `auth/limiter.py`, `auth/service.py::login` |
| Session theft | Random 256-bit tokens; `HttpOnly`, `SameSite=Lax`, `Secure` over HTTPS; 30-day absolute and 7-day idle lifetime; password change signs out other sessions; "sign out everywhere"; disabling a user kills their sessions immediately | `auth/service.py`, `auth/web.py` |
| CSRF | Per-session token in `X-CSRF-Token` on every POST/PUT/PATCH/DELETE; `Origin` must match `Host`; requests without `Content-Length` are refused, and so are chunked bodies (`Transfer-Encoding`), which would have no length to check | `auth/web.py`, `static/app.js`, `tests/test_hardening.py` |
| XSS | Per-request CSP nonce (`script-src 'self' 'nonce-...'`, `default-src 'none'`); no inline handlers; all dynamic text via `textContent`; links only if `https` on an allowed host; username HTML-escaped in the header | `auth/web.py::render_page`, all templates |
| SQL injection | Bound parameters everywhere; constants only in f-strings; tests scan the auth code for string-built SQL and throw injection strings at login | `auth/store.py`, `tests/test_auth.py` |
| SSRF (server fetching attacker-chosen URLs) | All outbound fetches go through `collector/http.py`: https only, host allow-list, redirects re-checked, every resolved address must be public, no IP-literal hosts or odd ports | `collector/http.py`, `tests/test_collector.py` |
| Hostile upload / path tricks | Needs the Upload permission; size cap (`MAX_UPLOAD_MB`, enforced on the real length: chunked bodies are refused); names sanitised and cut to 240 bytes (`safe_name`); a file must read as a song (the tag reader) or the whole upload is refused and removed; copied to disk in pieces (spooled under `reports/upload-tmp`, not memory); media file route checks the resolved path stays inside `MEDIA_ROOT` | `uploader.py`, `main.py`, `auth/web.py`, `tests/test_hardening.py` |
| Open redirect | `next` after login must be a same-site path | `auth/web.py::safe_next`, `templates/login.html` |
| Download page without sign-in | `/download` and `/api/downloads` are public so a new device can get the app before it has an account. They list only file names, versions and sizes of installers that are already public under `/static/` | `auth/web.py`, `tests/test_downloads.py` |
| Listener app served without sign-in | `/app/` is public so the login screen can load; it serves only static files built from `TOTRspa`, contains no data or secrets, and every `/api` call still needs a session and CSRF token. It has its own CSP (`APP_CSP`: scripts from itself only). The Electron/Android shells load it from the server, so whoever controls the server controls the app code (the shells are sandboxed with no Node access). Over plain HTTP a LAN attacker could tamper with it, which is another reason for HTTPS | `auth/web.py`, `tests/test_app_hosting.py` |
| Server updates | Only releases signed with the developer's Ed25519 key install: the signature covers a manifest that pins the bundle's SHA-256, size and version. The web app downloads and checks; a separate root service (`deploy/apply-update.py`) checks everything again, unpacks only plain files inside its own folder, goes forward only, backs up SQLite, and rolls back (database included) if the new version does not answer. The web app's user cannot write the code. PostgreSQL migrations need an administrator's login, used once and never stored. Downloads only from `github.com` / `githubusercontent.com` through `collector/http.py`. The signing key is the secret to protect (see `updates.md`) | `updates/`, `deploy/apply-update.py`, `tests/test_updates.py`, `tests/test_apply_update.py` |
| Information leaks | API docs disabled; `/health` returns one word; full health is admin-only; server errors show a generic JSON message with the security headers (details only in the log); invite links and join-request ids are hidden in the request log; no `Server` header | `main.py`, `auth/web.py`, `logredact.py`, `tests/test_hardening.py` |
| Destructive mistakes | Spider/collector changes need an admin click; files go to `.trash`; per-action precondition checks; an unmounted library proposes nothing | `spiders/actions.py`, `collector/acquire.py` |
| Per-person app data (`/api/me/data`) | Text the app stores for one person and hands back to them only: every query is limited to the signed-in person's id (never an id from the browser), names are a strict pattern, values are length-capped (30000 characters, 24 items), writes need the CSRF token. The server never interprets or renders the text; the app validates what it reads (themes go through the same checks as an imported file). Uses the existing `totr_auth` role, so no new credentials | `userdata/web.py`, `sql/user_data.sql`, `tests/test_userdata.py` |
| Desktop self-update (Windows, Linux) | The shell downloads the installer named in `latest.yml` / `latest-linux.yml` from the server and checks its SHA-512 from that file; nothing downloads until the person presses Install. Over https (app 0.5.2 and later, once the apps use `https://...:8443`) an attacker on the network cannot swap them; over plain http and with unsigned apps it stops damaged files only. Windows code signing is still not done | `TOTRspa/shared/electron/main.cjs`, `TOTRspa/shared/tools/deploy.cjs` |
| App self-update (Android) | The app downloads the APK named in `version.json` and gives it to Android's installer. Android installs it only if it is signed with the same key as the installed app, so a tampered or swapped file cannot replace TOTR (plain HTTP cannot protect the download itself; the signature does). The download is also checked against the SHA-256 in `version.json`. `/static/downloads/` is public on the LAN like the rest of `/static/`: an APK holds no secrets. The signing key (`TOTRspa/TOTRspa_apk/android/keystore/`) is the secret to protect: never commit it | `TOTRspa/TOTRspa_apk/android/.../Updater.java`, `TOTRspa/TOTRspa_apk/tools/release-apk.cjs` |
| HTTPS and the TOTR authority | `tlsconf.py` serves HTTPS next to (or instead of) HTTP; certificates come from `tools/make_certs.py`: an EC P-256 authority whose key is passphrase-encrypted, name-constrained (private addresses, `.local`, `.lan`; tested to refuse a public address or name) and unable to issue further authorities (`pathlen:0`). The server key is not password-protected (the server must start unattended) and lives only on the server with mode 600. The Windows/Linux app accepts the server certificate only if it is signed by the bundled authority, in date, for the exact address, and a private one (`electron/trust.cjs`, tested); Android trusts the authority through its network security config (`tools/sync-ca.cjs`). Android also stopped allowing backups of the app's data and is built as a release (not debuggable) | `TOTRsrv/tools/make_certs.py`, `tlsconf.py`, `tests/test_tls.py`, `TOTRspa/shared/electron/trust.cjs`, `tests/trust.test.cjs` |
| Native programs in the desktop app (IPC `native-launch`, `native-available`) | The page can only name `amp` or `fh`; the shell fixes the program (inside the installer's `resources/native`), its one argument (`--folder` under the person's home) and runs it without a shell. Calls are accepted only from the main frame of the app's own origin (not the offline page, another site or a sub-frame). The programs never use the network for TOTR; the shell copies only plain, plainly named files into their folders and never overwrites. Since the per-server controls (`shellaccess.cjs`) the page can press Open only if the person allowed that server's pages to use the app's controls (a dialog of the shell, once; the list is `access` in config.json). Residual risk as for any page-triggered action: whoever controls an allowed server controls the page that can press Open (the shell is sandboxed; the programs read only the person's own files and open no server connection) | `TOTRspa/shared/electron/native.cjs`, `main.cjs`, `tests/native.test.cjs` |
| Android offline mode | A switch the person flips (and which survives restarts) that closes the app up: `GuardClient.java` refuses every address except the app's own `https://localhost`, so the app neither reaches nor accepts anything on any network; the offline player is a bundled page with a strict CSP (`connect-src 'none'`). Saved songs live in the app's private storage and are served only to that page. Not covered: while online, the app trusts whatever answers at the saved server address (and that page can call `TotrNative`, including the installer): the launcher checks the address answers like TOTR but cannot prove who it is. Close with HTTPS and certificate pinning | `TOTRspa/TOTRspa_apk/android/.../GuardClient.java`, `OfflineStore.java`, `android-launcher/` |
| Clickjacking / MIME sniffing | `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, COOP/CORP, `Permissions-Policy` | `auth/web.py::security_headers` |

**Visual presets (FalseHorizon) are untrusted files.** A preset someone sends you can hold formulas, so they are never run as JavaScript: our own parser (no eval, no loops, 6000-character and 250-statement limits per formula, no access to the page, storage or network) turns them into arithmetic only, every number is clamped, the file is capped at 64 KB, and a preset's name or text is only ever shown with `textContent`. A flash guard limits brightness and how fast it can rise whatever a preset does. The MilkDrop importer treats a `.milk` file the same way (size-limited, only known keys read, numbers parsed as numbers, loops and memory arrays refused, every formula re-checked by the same parser); nothing is bundled and the person is told it is at their own risk. Tests: `tests/falsehorizon_test.js`, `tests/falsehorizon_milk_test.js`, `tests/test_visuals.py`.

## Meeting a new server (desktop apps)
A TOTR server made by the installer has its own certificate authority. When someone adds such a server in the desktop app (You > Servers, or the offline page), and the server's certificate is not one the app already trusts, the app fetches the authority the server offers (`/.well-known/totr-ca.pem`, public, certificate only) and shows its **fingerprint** (24 hex digits in six groups) in a native dialog of the app. The person compares it with the same code on the server's admin page (**Updates > This server > network identity**) or asks the admin. Only if they match do they press "The codes match: trust this server"; the authority is then saved in `config.json` (`pins`) for that server only (`electron/pins.cjs`). A certificate for that server from any other authority is refused, and the offline page says the certificate has changed. A pin is dropped when the server is removed. Plain `http://` servers are not asked about (nothing there is protected).

## Join requests
Off by default: an admin turns "Let people ask to join" on (Users page). The public endpoint `POST /api/join` takes a request signed by the app install's own key and writes one row; it creates no
account and no invite until an admin approves. Limits: 5 requests per address and 3 per install per hour, 200 waiting requests at most, text lengths capped, the history numbers whitelisted, the
signed clock within 10 minutes, one waiting request per install, a body cap of 64 KB (the gate). The server never stores or sends a secret for this: the app makes up its own one-time invite token and
sends only its hash, so reading the database does not give anyone a way in. **Honest limit:** the signature proves "the same install as before", not "an unmodified TOTR app"; anyone can make a key.
The admin page says so and shows the install's fingerprint, whether it asked before, and what the app reported about the person's other server (unverified). Tested in `tests/test_join.py`.

**Announcing on the network.** While (and only while) joining is switched on, the server announces itself by mDNS as `_totr._tcp` (`discovery.py`) so apps on the same network can list it. The record holds the server's name, its ports, the fingerprint of its certificate authority and `join=1`, and nothing private. With the switch off the server is silent. It needs UDP 5353 multicast to be allowed on the network and firewall; if it is not, the server logs one line and carries on, and apps can still add the server by address.

**In the desktop app** (`TOTRspa/shared/electron/discover.cjs`, `joinclient.cjs`): the list of "servers near you" is built from mDNS packets that anyone on the network can send, so it is treated as hostile: only the `_totr._tcp` shape is read, sizes and counts are capped, text is cleaned, and an announcement is ignored unless it comes from and points at a private, link-local or VPN address (10/8, 172.16/12, 192.168/16, 169.254/16, 100.64/10). The announced authority code is shown to compare, never trusted. Asking goes through the same trust question as adding a server (a friend's authority is compared by fingerprint first). Each install makes one Ed25519 key (`install-key.json`, owner-readable only) to sign requests; every request carries a fresh one-time invite token of which only the hash is sent. The token is kept in `config.json` until the invite is used (single use, 7 days, only valid after an admin approves). The page can ask and read answers; it never sees the token. Sharing counts from the person's current server is off unless they tick the box.

## Song offers
Nothing enters the library by itself. A person offers a list (title, artist, album, size, SHA-256); someone with the `upload` permission (or an admin) accepts some; only then does the server take
a file, and only from the person who offered it, for a song that was accepted, with exactly the offered size and checksum, and only if it reads as audio (a mutagen check, then the same save path as an
upload, so a name clash is refused and nothing is overwritten). The body of a send is limited to 300 MB (the offered size is checked first), a transfer that is cut off can be repeated, and an offer is
refused unless it is the signed-in person's own (someone else's id reads as "no such offer"). Who offered, who took what and what was added or refused is written to `reports/actions.log` (the audit file
the maintenance fixes use). When an admin asks a person for their songs, the person's tap on the request is the consent and the admin is recorded as the approver. The server cannot tell whether
the songs may legally be shared: that is the admin's judgement when accepting, as with the collector. On Android the phone asks the person on its own screen before it lists saved songs and before it sends any, and sends only to the server whose page is open. Limits: an offer is at most 100 songs and 4 GB, and a song is refused when the music disk would be left with under 1 GB. Tested in `tests/test_offers.py`.

## Secrets
- Live in `TOTRsrv/.env` (git-ignored). Never in code, tests, docs, commits or logs.
- The database password for each role is separate; one leak does not unlock another role.
- **Do not edit tracked SQL files with real passwords.** Copy the SQL into pgAdmin and change the placeholder there.
- The **database administrator's password** (Move to PostgreSQL, and the update service's `--continue`) is typed once, used once and never stored: it travels over https to a one-time helper on its standard input, not through arguments, environment, files or logs, and the helper's output is filtered so it cannot come back. The new roles' passwords are random and live only in `.env` (mode 600).
- If a secret is pasted into chat or a ticket, rotate it: `ALTER ROLE <role> PASSWORD '...'` then update `.env` and restart.

## Permissions (`auth/permissions.py`)
`admin` is a preset that holds every permission. A `member` holds none until an admin ticks some on the Users page. Stored as comma-separated names in
`users.permissions` (and `invites.permissions` for invites not yet used).

| Permission | Opens |
|---|---|
| `upload` | `/upload`, `/api/upload*` |
| `collector` | the Collector tab: `/api/collector*`, `/discover` |
| `maintenance` | the Maintenance tab: `/api/maintenance*` (run, approve, dismiss, ignore, schedule) |
| `status` | the Status tab: `/api/health`, `/status` |
| `settings` | site settings on the Account page: `/api/admin/settings` |
| `users` | the Users page and `/api/admin/users*`, `/api/admin/invites*` |

The Admin page (`/admin`) opens for anyone holding `status`, `maintenance` or `collector`; each tab still checks its own permission and the page hides the others.
The route table is `PERMISSION_PREFIX` in `auth/web.py` (first match wins). A path under `ADMIN_PREFIX` that is not in the table is reserved for the `admin` role, so a new admin route is closed by default. The Database page (`/admin/database`, `/api/admin/database`) is listed as admin-role only; it is read-only and its report never contains a password.
Rules (`auth/service.py`): you can only grant or remove permissions you hold yourself; nobody can change their own; admins' permissions cannot be edited; only an admin can invite, disable,
sign out or delete an admin. Changes apply on the person's next request.
On a database made before per-user permissions existed (until the owner runs `sql/user_permissions.sql`) the app uses the old two roles and the Users page says so (`service.has_permission_columns()`).

## Verifying
`python tests/run_all.py` runs ~280 security-relevant checks in `test_auth.py` (anonymous lockout, CSRF, roles, every permission against every protected route, grant rules, invites, user deletion, throttling,
session expiry, injection strings, open redirects, headers, forged cookies) and the network-guard checks in `test_collector.py`. A real browser
check under the strict CSP is done by loading every page in headless Edge and confirming zero policy errors.

## Known gaps and how to close them
1. ~~HTTPS exists but is not switched on yet.~~ A server made by the installer serves HTTPS with its own certificate authority; turn plain http off (`HTTP_ENABLED=false`) once the apps use https. The authority's key is the secret to protect (offline, backed up, never on the server or in git).
2. **Weak or shared database passwords.** Give each role its own long random password and rotate them after any paste into chat or a ticket ([hardening.md](hardening.md), section 3).
3. **Login throttling is in memory, per process.** Fine with one worker; move to the database before running several.
4. ~~Fonts come from Google Fonts.~~ Fixed 2026-10-09: the fonts are in `static/fonts/` (SIL Open Font License) and the CSP allows `'self'` only for styles and fonts.
5. ~~Uploaded files are validated by extension only.~~ Fixed 2026-10-15: the tag reader must recognise the file as audio. It is still a check of the container, not proof that every decoder will cope; the players are fuzzed (`threat-model.md`).
6. ~~The upload form reads whole files into memory.~~ Fixed 2026-10-15: copied in pieces, spooled to disk.
7. **No account lockout in the database** (by design, to avoid letting attackers lock real users out); throttling is the defence.

## Reporting and rules for contributors
To report a problem privately, see [`SECURITY.md`](../SECURITY.md). For running the server safely, see [hardening.md](hardening.md).
The rules: never weaken the gate, never add inline handlers, never string-build SQL, never fetch a URL outside `collector/http.py`,
never commit secrets.
